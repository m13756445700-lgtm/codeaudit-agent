# Command injection — execution context
Follow argument origin through wrappers. Identify actual executable and argument boundaries.
Java Runtime.exec(String) tokenizes arguments; it does NOT automatically invoke a shell. Shell metacharacters alone do not prove shell execution. ProcessBuilder(argv) and subprocess.run(argv, shell=False) also preserve argument boundaries, although executable/option injection can still matter.
Explicit sh -c, bash -c or cmd.exe /c interpret the command-string argument as shell syntax. If untrusted input reaches that string without complete context-appropriate protection, explain the reachable injection. Finite immutable server mappings can reject an apparent candidate. Do not confuse Runtime.exec("sh -c ...") tokenization with exec(new String[]{"sh","-c",command}); analyze the actual command argument.
Unknown custom runner implementation means insufficient evidence. Never execute payloads during code audit. Cite source, wrapper and final process invocation and state required endpoint access.

## Argument control is not automatically a security vulnerability
Whitespace tokenization can change argv without invoking another program. Before confirming CWE-88, identify a dangerous option of the actual fixed executable and a concrete security consequence (file write, code execution, credential exposure or boundary bypass). Merely changing formatting, printing help, or passing more ordinary data arguments is not sufficient. Distinguish untrusted data intentionally passed to a utility from control over a dangerous utility operation. Do not relabel a disproven shell-injection hypothesis as confirmed argument injection without new impact evidence. If a dangerous option is only conjectured, use INSUFFICIENT_EVIDENCE; reject the shell-injection hypothesis when shell interpretation is absent.
